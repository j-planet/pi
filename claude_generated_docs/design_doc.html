§1The short version

Pi is a coding agent you run in a terminal with the pi command. You type a request, and a language model reads files, runs commands and edits code through tools until the job is done. The repository builds that CLI as a stack of npm packages, and each one is useful on its own.

pi-ai

Talks to 42 LLM providers through one streaming interface.

pi-agent-core

Runs the loop: ask the model, execute the tools it calls, repeat.

pi-coding-agent

The product: coding tools, sessions on disk, extensions and four front-ends.

pi-tui

A terminal UI library that repaints only the lines that changed.

Four ideas explain most of the code.

  • Layers depend only downward. pi-ai knows nothing about agents. pi-agent-core knows nothing about files, terminals or disks. You can reuse any layer without the ones above it.
  • Everything is an event stream. Vendor chunks become AssistantMessageEvents. The loop wraps them as AgentEvents, and the session fans those out to persistence, extensions and whichever front-end is attached.
  • A session is an append-only tree. Every message, model switch and summary is one line in a .jsonl file. What the model sees next is computed from the active branch of that tree.
  • The core stays small and features plug in. Extensions are TypeScript modules loaded into the Pi process. MCP support and the codemode tool are themselves built-in extensions. Pi has no permission system. Isolation comes from the operating system or a container.

Colour key used throughout

  • pi-ai
  • pi-agent-core
  • pi-coding-agent
  • pi-tui
  • supporting / experimental

§3Life of a prompt

Follow one request from the keyboard to the disk. The diagram shows the interactive front-end. Print, JSON and RPC modes replace only the left-most column.

  1. You press Enter. InteractiveMode passes the text to AgentSession.prompt(), which runs extension input handlers, handles extension slash commands and expands prompt templates.
  2. AgentSession hands the message to Agent.prompt() in pi-agent-core. Before each request the loop turns its AgentMessage[] into plain LLM messages with convertToLlm.
  3. The loop calls its streamFn, which pi-coding-agent wires to ModelRuntime.streamSimple(). pi-ai resolves auth (stored credential first, then environment variables, refreshing OAuth tokens when needed), finds the provider that owns the model, loads that provider's wire-protocol module on first use and opens the HTTP stream.
  4. Streamed chunks come back as normalized AssistantMessageEvents. The loop re-emits them as message_update. AgentSession gives each event to extensions first, then to listeners such as the TUI, which schedules a repaint.
  5. On message_end, AgentSession appends the finished message to the session file.
  6. If the reply contains tool calls, the loop runs them (in parallel by default), emits tool_execution_* events, appends each result and starts another turn.
  7. When no tool calls or queued messages remain, the loop emits agent_end. AgentSession may still auto-retry a failed request, or compact the context and retry after a context-overflow error.

Each layer only produces events and reacts to hooks. The loop has no idea a disk exists, so the same Agent class can run inside the CLI, the SDK, a browser app (through streamProxy) or a chat bot. Front-ends only subscribe to events, which is how four of them share one AgentSession.

§4One interface to many LLMs packages/ai

pi-ai answers one question: given a conversation and a model, stream back the reply in a shape that does not depend on the vendor. Three nouns carry the design.

Model
Plain JSON data: id, provider, api, baseUrl, context window, prices and thinking support. No functions are attached, so a session file can record which model answered as ordinary text.
Provider
A runtime object that owns a model catalog, its auth (API keys, environment variables, OAuth logins) and a stream implementation. Built with createProvider(). There are 42 built-in factories in src/providers/.
API implementation
One wire protocol, such as anthropic-messages or openai-completions. Each module in src/api/ exports stream and streamSimple. Many providers share one.

A Models collection holds the providers. Its stream() method normalizes the context, merges the provider's auth into the request, and then dispatches to the provider that owns the model.

Every provider's reply ends up in the same few types, defined in src/types.ts:

type Message = SystemMessage | UserMessage | AssistantMessage | ToolResultMessage;

interface AssistantMessage {
  role: "assistant";
  content: (TextContent | ThinkingContent | ToolCall)[];
  api: Api; provider: string; model: string;
  usage: Usage;           // tokens plus computed cost for this reply
  stopReason: StopReason; // "stop" | "toolUse" | "length" | "error" | "aborted" | …
  timestamp: number;
}
  • One event shape keeps every layer above vendor-neutral and lets you switch models mid-conversation. When one vendor's message is sent to another, its thinking blocks become <thinking> text and everything else passes through unchanged.
  • Lazy SDK loading. A provider imports a tiny *.lazy.ts wrapper, and the heavy SDK (@anthropic-ai/sdk, openai, @google/genai, AWS) loads on the first request. Startup stays fast, bundles stay small, and the core entrypoint bundles cleanly for browsers.
  • The system prompt and tool list live inside the transcript as system messages. A later system message can patch named prompt sections or add and remove tools. Models that accept mid-conversation system messages get the patch in place, which keeps the cached prompt prefix valid. Other models get the replayed prompt collapsed into the first message.
  • Auth belongs to the provider. A stored credential owns its provider, and environment variables are read only when nothing is stored. OAuth refresh runs inside CredentialStore.modify(), a serialized read-modify-write, so two concurrent requests cannot both refresh one token.
  • TypeBox tool schemas are plain JSON with built-in validation, so tool definitions can be stored and sent over the wire.

The model catalog is generated. scripts/generate-models.ts pulls models.dev and the OpenRouter listing, applies hand-written corrections and writes src/providers/data/*.json. That folder is git-ignored and created at build time. Typed wrappers such as anthropic.models.ts import the JSON. Fix the script and never hand-edit the output.

§5The agent loop packages/agent

pi-agent-core turns a single model call into an agent. It calls the model, runs the tools the model asked for, feeds the results back and repeats until the model stops asking. The public surface is the Agent class in src/agent.ts. The loop itself is runLoop() in src/agent-loop.ts.

Mechanics worth knowing

AgentMessage
The agent stores AgentMessages. These are the four LLM roles plus custom roles an app adds through TypeScript declaration merging. pi-coding-agent adds bash executions, compaction summaries and extension messages. Before each request, transformContext (optional) and convertToLlm (required) reduce them to what the model understands.
Steering vs follow-up
A steering message, typed while the agent works, is delivered after the current turn's tools finish. A follow-up waits until the agent would otherwise stop. Each queue delivers either one message at a time or all queued messages at once.
Parallel tools
For each call in order, arguments are validated and beforeToolCall runs (it can block the call). The allowed tools then run concurrently. Results are appended in the order the model asked for them, whatever order they finished in. One tool marked sequential makes its whole batch sequential. A tool reports failure by throwing, and the model receives an error result.
Truncated replies
If a reply hit the output token limit (stopReason: "length"), every tool call in it fails without running, because its JSON arguments may be cut off.
Tool loadout
Before each request the loop compares the tools it can execute with the tools the transcript has declared. If they differ, it appends a system message with toolsAdded and toolsRemoved.

The loop owns control flow and nothing else. Everything app-specific enters through hooks (prepareRequest, beforeToolCall, afterToolCall, finishTurn, the queue polls) and leaves through events. pi-coding-agent adds persistence, compaction, retries and extensions without forking the loop, and the same package can back a web app or a Slack bot.

Heads-up: two generations in one package

src/agent.ts and src/agent-loop.ts are what pi runs today. src/harness/ holds a newer durable harness (AgentHarness, lanes, durable operations and the experimental pico3 kernel), started on 2026-05-03. Only coding-agent/src/experimental/ uses it, and that folder is excluded from the published npm package.

pi-coding-agent also keeps its own compaction and session code in src/core/, next to similar modules under agent/src/harness/. To fix a CLI bug, start in coding-agent's core/ and agent's agent-loop.ts.

§6The coding agent runtime packages/coding-agent

pi-coding-agent holds 42% of the source (83,756 lines). Most of it serves one idea: a single AgentSession does the work, and thin front-ends handle input and output around it.

Startup, in order (src/main.ts)

  1. Sub-commands that need no session (pi install / remove / update / list, pi config, pi mcp, auth commands) run and exit.
  2. parseArgs() reads the flags. resolveAppMode() picks interactive (a TTY), print (-p or piped stdin), JSON or RPC.
  3. Migrations run, settings load, and createSessionManager() opens a new, continued, resumed or forked session.
  4. createAgentSessionRuntime() calls a factory that resolves project trust, builds the services (ModelRuntime, SettingsManager, ResourceLoader) and then creates the AgentSession.
  5. The chosen mode runs: InteractiveMode.run(), runPrintMode() or runRpcMode().

What AgentSession adds on top of Agent

  • Persists every finished message and every model or thinking-level change.
  • Compaction, both manual (/compact) and automatic, plus overflow recovery.
  • Auto-retry for retryable provider errors.
  • Model cycling and thinking-level control, clamped to what the model supports.
  • !command shell execution recorded into the conversation.
  • Branching, forking and /tree navigation.
  • Binding extensions: their tools, commands and event handlers.

Built-in tools live in src/core/tools/, which defines eight tool names: read, bash, edit, write, grep, find, ls and powershell. The first four are active by default (DEFAULT_TOOL_NAMES). Tool calls can run in parallel, so every file-changing tool wraps its read-modify-write in withFileMutationQueue(), which serializes work per real file path.

The system prompt is built in src/core/system-prompt.ts as named sections: a preamble, tool snippets and guidelines, context files such as AGENTS.md, skills and the working directory. Those sections become the sections of the session's first system message, so later changes are small patches.

One core, many shells. Interactive, print, JSON, RPC and the SDK all drive the same AgentSession, so a fix to retries or compaction lands everywhere at once. Services are rebuilt per working directory because /resume can open a session that belongs to another project, and that session needs its own project's settings, extensions and models. The runtime keeps its factory and calls it again for /new, /resume, /fork and imports.

§7Sessions: a tree in a JSONL file

Sessions are stored at ~/.pi/agent/sessions/--<path>--/<timestamp>_<id>.jsonl. The first line is a header. Every other line is an entry with an id and a parentId, so the entries form a tree. The leaf is the entry you are on now, and the path from the root to the leaf is the active branch.

An abbreviated session file looks like this:

{"type":"session","version":3,"id":"…","cwd":"/project"}
{"type":"message","id":"a1b2c3d4","parentId":null,"message":{"role":"user","content":"Hello"}}
{"type":"message","id":"b2c3d4e5","parentId":"a1b2c3d4","message":{"role":"assistant","content":[{"type":"text","text":"Hi!"}],"provider":"anthropic","model":"claude-sonnet-4-5",…}}
{"type":"model_change","id":"c3d4e5f6","parentId":"b2c3d4e5","provider":"openai","modelId":"gpt-4o"}
{"type":"compaction","id":"d4e5f6a7","parentId":"c3d4e5f6","summary":"User discussed X…","firstKeptEntryId":"b2c3d4e5","tokensBefore":50000}

Shapes the model context

  • message · one AgentMessage
  • compaction · summary plus prompt checkpoint
  • branch_summary · what an abandoned branch tried
  • custom_message · extension-injected content
  • context_edit · hides or rewrites an earlier entry

Metadata only

  • model_change, thinking_level_change
  • usage · cost of side work such as cache warming
  • custom · extension state
  • label · a bookmark on an entry
  • session_info · the session's display name

How the next request is built

  1. buildContextEntries() walks from the leaf to the root. If a compaction is on the path, it keeps the latest one, the entries from its firstKeptEntryId onward, and everything after it.
  2. buildSessionProjection() applies context_edit entries, which omit or replace an earlier message for future requests only.
  3. buildSessionContext() turns the entries into messages and reads the current model and thinking level from the path.

Compaction runs automatically when contextTokens > contextWindow − reserveTokens, with reserveTokens defaulting to 16,384. Pi keeps roughly the newest keepRecentTokens (default 20,000) and asks the model to summarize everything older. The original entries stay in the file.

  • Append-only writes are cheap and survive crashes. A run that dies halfway loses at most the line being written.
  • Branching needs no copies. /tree moves the leaf, the abandoned path stays in the file, and a branch_summary tells the new branch what was already tried.
  • Context is a view over history. Compaction and context edits change what the model sees next without destroying anything, so exports, the UI and cost totals still see the full record.
  • JSONL is easy to inspect with grep, jq or a ten-line script. Older formats (v1 linear, v2 tree) migrate to v3 when loaded.

§8Extensions, resources and trust

An extension is a TypeScript module whose default export receives pi: ExtensionAPI. It can register tools, slash commands, shortcuts, CLI flags, model providers, MCP servers, renderers and UI. It can also subscribe to lifecycle events with pi.on(). Here is a trimmed version of examples/extensions/permission-gate.ts:

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName !== "bash") return undefined;
    const command = event.input.command as string;
    if (/\bsudo\b/.test(command) && !(await ctx.ui.confirm("Allow sudo?", command))) {
      return { block: true, reason: "Blocked by user" };   // the model sees this as a tool error
    }
  });
}

Where extensions can step in during a run

  1. Input
  2. inputcan change

    Continue, transform the submitted text, or mark it handled.

  3. before_agent_startcan change

    Adjust prompt sections, tools or guidelines for this run, or replace the whole prompt.

  4. Building the request
  5. context · context_with_systemcan change

    Rewrite the message list sent to the model. Nothing is persisted.

  6. before_provider_headers · before_provider_requestcan change

    Edit HTTP headers or the raw provider payload.

  7. Streaming
  8. provider_stream_eventobserve

    See each parsed vendor event before normalization.

  9. message_update · message_endend can change

    Watch streaming. message_end can replace the finished message.

  10. Tools
  11. tool_callcan block

    Mutate arguments or block the call. A handler that throws also blocks, as a fail-safe.

  12. tool_resultcan change

    Rewrite the result. Handlers compose in load order.

  13. End of turn and run
  14. turn_endcan continue

    Append entries and request one more model call.

  15. agent_before_settlecan continue

    The last point where an extension can append entries or keep the run going.

  16. agent_settledobserve

    Pi will not continue on its own after this.

Session events (session_start, session_shutdown, session_compact, session_tree and others) bracket all of this. src/core/extensions/types.ts declares every event with its exact result type.

Loading

Extensions load from ~/.pi/agent/extensions/, from .pi/extensions/ in a trusted project, from Pi packages, or from --extension <path>. Pi compiles TypeScript on the fly with jiti, so there is no build step. Imports of @earendil-works/pi-* (and the legacy @mariozechner/pi-* scope) are aliased to the copies already running, so an extension and Pi share one instance of every class and type.

Pi uses its own extension API for several built-in features. src/extensions/ holds MCP support, codemode, tool_search and llama.cpp, registered as built-in extensions. The first three are marked replaceable: a third-party extension that registers the same tool or command takes over.

Project trust. Before loading .pi/settings.json, .pi/mcp.json, project extensions and other protected project resources, Pi asks whether you trust the folder, because extensions run code. Trust controls loading only. Tools still run with your account's permissions, and the docs recommend a container or VM for real isolation (docs/containerization.md).

Pi describes itself as self-extensible. The core stays small, and the agent can write extensions for you. Plan mode, sub-agents, permission prompts, sandboxing and git checkpoints exist as extension examples (79 entries in examples/extensions/) and stay out of the core. The cost is power: an extension can read prompts, files and credentials, and nothing inside the process sandboxes it.

§9Differential rendering packages/tui

pi-tui is a small terminal UI framework with no dependencies on the rest of Pi. A component implements render(width): string[], which returns one string per terminal line, and optionally handleInput(data). Containers stack their children, and the renderer decides what to repaint.

Two renderers implement the same TUI interface. TuiMainScreen, the default regular mode, writes into the normal terminal buffer, so your scrollback survives. TuiAltScreen (--tui-mode fullscreen) owns an alternate-screen viewport with its own scrolling, mouse support and text selection.

The main-screen renderer has three strategies. The first render prints everything. A width change, or a change above the visible viewport, forces a full redraw. Every other update rewrites from the first changed line. requestRender() coalesces calls through process.nextTick and keeps at least 16 ms between frames.

A streaming reply triggers many updates per second. Repainting the whole screen each time flickers and wipes scrollback. Diffing plain strings is cheap, and components that return strings are easy to test: packages/tui/test/virtual-terminal.ts renders into a fake terminal.

§10Around the core

The remaining packages either support the four core packages or explore where Pi is heading. You can ignore the experimental ones while you learn the CLI.

chord 8,808

Application-composition runtime. Plugins split into facets that run in different processes, with typed services, replicated state and RPC. It has no Pi dependencies. pi-agent-core, pi-coding-agent and the experimental packages depend on it.

pi-telemetry 935

Vendor-neutral span and event contracts with a no-op default and an in-memory reference implementation. Packages pass a TelemetryContext explicitly, with no global state.

pi-mcp 3,057

A small Model Context Protocol client (stdio and Streamable HTTP) that does not depend on the official MCP SDK. The built-in MCP extension uses it.

pi-codemode 1,600

Runs model-written JavaScript in a QuickJS WebAssembly VM whose only capability is calling injected tools. Nested tool calls stay out of the model's context.

pi-durable 17,377 · experimental

A durable agent runtime that commits turns and tool calls to storage before showing them, so a crashed process resumes where it stopped. No other package uses it yet.

protocol · client · server 869 · 1,135 · 1,966

Length-prefixed CBOR frames, a transport-neutral client and a local server that routes calls to session workers. With coding-agent/src/experimental/ they explore running a session in its own process with several UIs attached.

sqlite backend 1,973

SQLite storage for harness sessions. It is a separate package so pi-agent-core does not pull in native SQLite.

pi-evals 1,446

Behavioral evals built on vitest-evals, including "documentation lift" runs that compare Pi with and without its docs inside Docker.

§11Design decisions and trade-offs

Here are the choices that shape the codebase, with what each one buys and what it costs.

DecisionProblem it solvesWhat it costs
Separate packages, downward-only dependenciespi-ai and pi-agent-core are reused by the SDK, browser apps and other projects such as pi-chat. Each layer is tested alone.14 package folders to build in order and version in lockstep.
Normalized event streams at every layerOne UI-agnostic core powers four front-ends. Extensions and persistence are just more listeners.Event shapes become a public contract for RPC and JSON consumers.
Append-only JSONL tree for sessionsCrash safety, cheap branching, full history for exports and cost totals.Context must be recomputed as a projection, and files only grow.
In-process TypeScript extensions, with built-ins as extensionsSmall core, fast iteration, deep customization without forking.No sandbox. Project extensions need a trust prompt.
No built-in permission systemAvoids a false sense of safety. The OS or container is the real boundary.Users who need isolation must set up a container or VM.
Lazy provider SDKs and a generated catalogFast startup and small bundles. Metadata for 42 providers without hand maintenance.A normal build fetches catalog data over the network (build:offline skips it).
Prompt and tools carried inside the transcriptMid-session changes stay cache-friendly and replayable.Provider adapters must handle system messages mid-conversation.
Erasable-only TypeScript, run with plain NodeSources run without a build step (TypeScript 7 plus Node's type stripping).No enum, namespace or constructor parameter properties.
Pinned dependencies, shrinkwrap, --ignore-scriptsSupply-chain safety for a tool that runs with your permissions.Upgrades are deliberate, manual reviews.

Everything from prompt() to agent_end: one or more turns.
steering message
Input typed while the agent works, delivered after the current turn's tools finish.
follow-up
Input queued for when the agent would otherwise stop.
provider
A vendor account or endpoint (Anthropic, Groq, OpenRouter). Owns auth and a model catalog.
API (wire API)
The HTTP protocol a provider speaks, such as openai-completions. Many providers share one.
thinking level
Pi's vendor-neutral reasoning effort: off, minimal, low, medium, high, xhigh, max. Clamped to what the model supports.
entry
One line of a session file, with an id and a parentId.
leaf / active branch
The current entry, and the path from it back to the root.
compaction
An entry that replaces older context with an LLM summary for future requests.
context edit
An entry that hides or rewrites an earlier message for future requests only.
extension
A TypeScript module loaded into Pi that registers tools, commands, hooks or UI.
skill
On-demand instructions plus supporting files. Only the name and description sit in the prompt.
prompt template
Reusable message text exposed as a slash command.
Pi package
A bundle of extensions, skills, prompts and themes installed from npm or git.
project trust
Your decision to let a folder's .pi/ resources load.
facet / service
Chord's units: part of a plugin that runs in one process, and a typed token that facets provide or require.
lane
A unit of work in the newer durable AgentHarness, used only by experimental code today.

§14Working in the repo

  • npm install --ignore-scriptsInstall dependencies without running lifecycle scripts.
  • ./pi-test.shRun pi straight from source. Node loads the TypeScript through a resolver hook, so nothing is built first.
  • npm run checkBiome lint and format, type checking, dependency and import checks. Run it after code changes.
  • ./test.shAll non-e2e tests. Avoid running the full vitest suite directly, because e2e tests switch on when API keys are present.

AGENTS.md at the repo root holds the house rules for humans and agents alike: erasable TypeScript only, top-level imports only, exact-pinned dependencies, changelog entries under ## [Unreleased], and session tests through test/suite/harness.ts with the faux provider.

The user-facing docs in packages/coding-agent/docs/ (39 files) are the best next read. Start with how-pi-works.md, extensions.md and session-format.md.
