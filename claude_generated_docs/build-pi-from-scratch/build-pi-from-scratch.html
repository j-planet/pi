Build Pi From Scratch

You know how a transformer turns tokens into a next token. This page climbs from there to a working coding agent in eight steps of Python. Each step starts with a concrete failure of the previous one and adds exactly one idea, then points to the pi code that does the same job. The Python is my own teaching code, written to mirror pi's TypeScript; it is not in the repo.

§1The missing bridge

Between "a transformer predicts tokens" and "pi fixes my failing test" sit three rungs that the model vendor builds and three that a harness like pi builds. A harness is the ordinary program around the model: it sends requests, runs tools and keeps the conversation.

Four ideas carry the whole climb:

  1. The model is stateless. Every call sends the full conversation (the transcript). The transcript is the agent's only memory.
  2. A tool call is text the model was trained to write. The model never runs anything. Your code reads the call, runs it, and pastes the result back into the transcript.
  3. The agent loop is autoregression one level up. Decoding repeats "predict a token, append it" until an end token. An agent repeats "get a reply, append it plus tool results" until a reply has no tool calls (Fig 3).
  4. Everything else is engineering for real use: failures, live display, safety policy, interruptions and context limits. That is most of pi.

If you know reinforcement learning, this mapping may help. It is my framing; the ReAct paper (Yao et al., 2022) popularised the reason-then-act loop.

RL termAgent termExample
policythe LLMClaude, GPT, Gemini
actiona tool callbash {"command": "pytest -x"}
environmentyour tools plus the filesystemthe repo on disk
observationa tool result"1 failed, 4 passed"
episode enda reply with no tool calls"Fixed the off-by-one."

One difference matters: nothing here is trained. The policy is frozen, and the "state" is the transcript the policy reads.

§2Step 0 · The LLM is a function

Idea. Treat the model as an async function: llm(messages, tools) → assistant message. A provider's chat template turns the messages into one token sequence with role markers, the model generates until its end-of-turn token, and the API hands back a parsed message.

The transcript is a list of dicts, oldest first. Each message has a role. Our shapes copy pi's: user, assistant and toolResult (packages/ai/src/types.ts:548-612).

# The transcript: plain dicts, oldest first.
messages = [{"role": "user", "content": "What port does config.json use?"}]

class FakeLLM:
    """Replays scripted replies in order, like a mock in a unit test."""

    def __init__(self, replies):
        self.replies = list(replies)

    async def __call__(self, messages, tools):
        return self.replies.pop(0)          # ignores its input on purpose

Why a fake model first? It makes every run free and repeatable, so you can test the loop the way you would unit-test a training step with a fixed batch. pi does the same: its tests drive the loop with scripted replies (packages/agent/test/agent-loop.test.ts:127-172), and pi-ai ships a "faux" provider with helpers such as fauxToolCall() (packages/ai/src/providers/faux.ts:62).

Why its own message format? pi talks to many providers (packages/ai/src/providers/ has Anthropic, OpenAI, Google, Bedrock, Groq, DeepSeek and more). It keeps one neutral transcript and converts it per provider at the last moment. You will write one such converter in Step 1.

§3Step 1 · One tool call

Problem. Ask "What port does config.json use?" and a bare model can only guess, because it cannot see your disk.

Idea. Describe a function to the model. When it wants that function, it writes a structured call instead of prose. Fig 2 shows what happens at the token level.

A tool has four parts: a name, a description, a parameter schema, and a function. The first three are sent to the model as text. The description is a prompt. The model picks tools by reading it, so wording matters as much as code. Here a pydantic model is the schema. pi uses TypeBox, the TypeScript counterpart, as in the bash tool's command and timeout parameters (packages/coding-agent/src/core/tools/bash.ts:41-42).

from pydantic import BaseModel, Field

class ReadFile:
    name = "read_file"
    description = "Read a UTF-8 text file and return its contents."

    class Params(BaseModel):                # becomes JSON Schema for the model
        path: str = Field(description="Path relative to the project root")

    async def execute(self, call_id, args):
        text = open(args.path).read()       # blocking I/O; fine for a sketch
        return [{"type": "text", "text": text}]

tools = {"read_file": ReadFile()}

One round trip takes two model calls: one to get the call, one to read the result. With a fake model scripted for both replies:

llm = FakeLLM([
    {"role": "assistant", "stop_reason": "toolUse", "content": [
        {"type": "toolCall", "id": "call_1", "name": "read_file",
         "arguments": {"path": "config.json"}}]},
    {"role": "assistant", "stop_reason": "stop",
     "content": [{"type": "text", "text": "It uses port 8080."}]},
])

reply = await llm(messages, tools)                    # 1. the model writes a call
messages.append(reply)
call = next(b for b in reply["content"] if b["type"] == "toolCall")
tool = tools[call["name"]]
args = tool.Params.model_validate(call["arguments"])  # JSON -> typed object
content = await tool.execute(call["id"], args)        # 2. YOUR code runs it
messages.append({"role": "toolResult", "toolCallId": call["id"],
                 "content": content, "isError": False})
reply = await llm(messages, tools)                    # 3. the model reads the result

The toolCallId pairs each result with its call, like a join key. The model needs it when one reply asks for several tools.

Optional: swap in the real Claude

The adapter below converts our transcript to Anthropic's format and back. It is the Python version of what pi-ai does in packages/ai/src/api/anthropic-messages.ts: tool_use becomes toolCall (:723-733), results become tool_result blocks (:1294-1300), consecutive results share one user message (:1462-1467), and stop reasons are renamed (:1617-1625). The two fallbacks lines ask the API to retry on another model if this one declines; delete them if you prefer.

import anthropic

client = anthropic.AsyncAnthropic()           # reads ANTHROPIC_API_KEY
STOP = {"end_turn": "stop", "tool_use": "toolUse",
        "max_tokens": "length", "refusal": "error"}

def to_api(messages):
    """Convert our transcript to Anthropic's wire format."""
    out = []
    for m in messages:
        if m["role"] == "assistant":          # echo the raw blocks unchanged
            out.append({"role": "assistant", "content": m["raw"]})
        elif m["role"] == "toolResult":
            block = {"type": "tool_result", "tool_use_id": m["toolCallId"],
                     "content": m["content"], "is_error": m["isError"]}
            if out and out[-1]["role"] == "user" and isinstance(out[-1]["content"], list):
                out[-1]["content"].append(block)   # one user message per batch
            else:
                out.append({"role": "user", "content": [block]})
        else:
            out.append({"role": "user", "content": m["content"]})
    return out

async def claude_llm(messages, tools):
    """Same signature as FakeLLM, so the loop cannot tell them apart."""
    resp = await client.beta.messages.create(
        model="claude-opus-5-5", max_tokens=16000,
        betas=["server-side-fallback-2026-07-01"], fallbacks="default",
        tools=[{"name": t.name, "description": t.description,
                "input_schema": t.Params.model_json_schema()} for t in tools.values()],
        messages=to_api(messages))
    content = [{"type": "text", "text": b.text} if b.type == "text" else
               {"type": "toolCall", "id": b.id, "name": b.name, "arguments": b.input}
               for b in resp.content if b.type in ("text", "tool_use")]
    return {"role": "assistant", "content": content, "raw": resp.content,
            "stop_reason": STOP.get(resp.stop_reason, "stop")}
Where the agent's "skill" lives

Notice how little code that is. All the competence (choosing read_file, picking the path, reading the answer) comes from the model. The harness supplies hands and memory, not judgment.

§4Step 2 · The loop

Problem. Step 1 hard-codes exactly one tool call. Real tasks need an unknown number. "Fix the failing test" means: run the tests, read the file, edit it, run the tests again, then report.

Idea. Keep calling the model until a reply contains no tool calls. That while loop is what turns a tool-calling model into an agent.

async def run_agent(messages, tools, llm):
    """Call the model until it stops asking for tools."""
    while True:
        reply = await llm(messages, tools)
        messages.append(reply)
        calls = [b for b in reply["content"] if b["type"] == "toolCall"]
        if not calls:
            return reply                            # the model is done
        for call in calls:
            tool = tools[call["name"]]
            args = tool.Params.model_validate(call["arguments"])
            content = await tool.execute(call["id"], args)
            messages.append({"role": "toolResult", "toolCallId": call["id"],
                             "content": content, "isError": False})

Here is a five-turn run of "make the tests pass". A turn is one reply plus the tools it asked for (packages/agent/src/types.ts:518).

TurnModel writesYour code appends
1bash {"command": "pytest -x"}"FAILED test_parse: expected 3, got 2"
2read {"path": "parser.py"}the file's text
3edit line 14: < → <="Edited parser.py"
4bash {"command": "pytest -x"}"5 passed"
5"Fixed an off-by-one in parser.py."nothing: no calls, so stop

A cost you should see coming. Turn 5 re-sends everything from turns 1–4, because the model is stateless. Total input therefore grows roughly with the square of the turn count. Providers soften this with prompt caching, which reuses the attention keys and values (the KV cache) of an unchanged prefix. That is why harnesses only ever append to the transcript: an edit early on breaks the cached prefix. pi's coding agent even keeps that cache warm between requests (packages/coding-agent/src/core/sdk.ts:396-406).

pi's real loop is runLoop() (packages/agent/src/agent-loop.ts:163-321). Condensed, it is the same shape plus a queue of messages the user typed mid-run (Step 6):

§5Step 3 · Errors are data

Problem. Step 2 crashes on the model's first mistake, and models make mistakes:

FailureExampleStep 2 behavior
unknown toolcalls read_filesKeyError, run dies
bad arguments{"file": "a.py"} instead of pathValidationError, run dies
tool raisesthe file does not existFileNotFoundError, run dies
reply cut offhit the output-token cap mid-JSONmay run half-written arguments

Idea. Turn every failure into a tool result with isError: True. The model reads the error and retries, much as a client corrects a request after a 422 response from a web API. A crash would throw away all the turns so far.

async def run_tool(call, tools, truncated):
    """Run one call. Every failure becomes a result the model can read."""
    try:
        if truncated:                     # stop_reason "length": JSON may be cut off
            raise ValueError("Your reply was cut off. Re-issue the call.")
        tool = tools.get(call["name"])
        if tool is None:
            raise LookupError(f"Tool {call['name']} not found")
        args = tool.Params.model_validate(call["arguments"])
        return await tool.execute(call["id"], args), False
    except Exception as e:
        return [{"type": "text", "text": str(e)}], True

Two lines change in the loop. Provider failures (stop_reason of error or aborted) are the one hard exit. Everything else becomes data:

        if reply["stop_reason"] in ("error", "aborted"):
            return reply                                  # provider failed: stop
        ...
            content, is_error = await run_tool(call, tools, reply["stop_reason"] == "length")

pi splits this into gates: prepareToolCall() finds the tool and validates arguments (agent-loop.ts:707-776, using validateToolArguments from packages/ai/src/utils/validation.ts:317), and a truncated reply fails every call (agent-loop.ts:264-270). The comment there says such calls may carry "truncated arguments".

§6Step 4 · Events and streaming

Problem 1. A long reply can take many seconds. With Step 3, the screen stays blank until it is complete.

Problem 2. Several parts of a product need to know what happens: the terminal display, a session file on disk, a cost meter. Putting print() and file.write() inside the loop ties the loop to every one of them.

Idea. The loop announces what happens as events, and any number of subscribers react. This is the observer pattern, like callbacks in a training framework. Streaming then becomes one more kind of event.

subscribers = [draw_terminal, append_to_session_file, count_tokens]

async def emit(event):
    """Tell every subscriber, one at a time, in order."""
    for fn in subscribers:
        await fn(event)

async def stream_reply(messages, tools, llm_stream):
    """Show the reply while it is being generated."""
    await emit({"type": "message_start"})
    async for event in llm_stream(messages, tools):   # waits for each chunk
        if event["type"] == "text_delta":
            await emit({"type": "message_update", "delta": event["delta"]})
        elif event["type"] in ("done", "error"):
            await emit({"type": "message_end", "message": event["message"]})
            return event["message"]
Async in one paragraph

While the model generates, your process is mostly waiting on the network. asyncio runs many tasks on one thread. Each await is a point where a task says "I'm waiting; run something else." So between chunks of the reply, the same thread can redraw the screen or notice that the user pressed Esc. async for is a for loop whose "get next item" step may wait. No threads, no locks: tasks switch only at await.

pi's loop emits ten event types: agent_start/agent_end, turn_start/turn_end, message_start/message_update/message_end, and tool_execution_start/_update/_end (packages/agent/src/types.ts:514-529). A real subscriber: the coding agent writes each finished message to the session file on message_end (packages/coding-agent/src/core/agent-session.ts:1115-1133). Here is pi's stream consumer, condensed:

for await (const event of response)
async for event in response:.
switch / case / break
match/case. Without break, TypeScript would fall through into the next case.
{ ...event.partial }
A shallow copy, {**d}. My reading: subscribers get a snapshot that later deltas will not change.
result()
An awaitable that resolves when the stream finishes, like an asyncio.Future (packages/ai/src/utils/event-stream.ts:86-88).

Note that the partial reply sits in the transcript while it streams, then the final message replaces it. And because emit awaits each subscriber, a slow subscriber slows the agent; pi accepts that cost so every subscriber sees events in order (packages/agent/src/agent.ts:609-611).

§7Step 5 · Hooks

Problem. Different products need different policies, and each wants a different edit to the loop. Ask before running rm -rf. Trim history when the context window fills. Stop after 50 turns. Editing run_agent for each one means a fork per product.

Idea. Leave a named slot (a hook) at each decision point, and let the product plug in functions. It is how Keras callbacks or Lightning hooks let you change training without editing fit().

config = {
    "transform_context": keep_last_100_messages,   # before each model call
    "before_tool_call":  ask_user_first,           # may block a call
    "finish_turn":       stop_after_50_turns,      # may end the run
}

# Inside the loop:
view = await config["transform_context"](messages)   # the model sees this view;
reply = await llm(view, tools)                       # the transcript keeps everything
...
blocked = await config["before_tool_call"](call, args)
if blocked:
    content, is_error = [{"type": "text", "text": blocked["reason"]}], True
...
if await config["finish_turn"](turn) == {"action": "end"}:
    return reply

pi has seven such hooks on AgentLoopConfig (packages/agent/src/types.ts:193-342). The coding agent really uses them:

HookWhen it runspi's coding agent plugs in

convertToLlmbefore each model calldrops app-only messages, attaches images (sdk.ts:395)

Note the split in transform_context: the model sees a trimmed view, while the transcript stays complete. Like a dataloader's transform, it changes what the model sees without touching the stored data.

§8Step 6 · The Agent class

Problem. A real user does four things a function call cannot handle:

  1. Types "actually, use port 9090" while the agent is working.
  2. Presses Esc to stop it.
  3. Sends the next prompt, which must continue the same conversation.
  4. Gets a reply asking to read five files at once, and waits through five sequential reads.

Idea. Wrap the loop in a class that owns the transcript across runs, two queues, and a cancel flag. Run independent tool calls concurrently.

class Agent:
    """Owns the transcript between runs and feeds the loop."""

    def __init__(self, llm, tools):
        self.llm, self.tools, self.messages = llm, tools, []
        self.steering, self.follow_ups = [], []    # messages typed mid-run
        self.cancel = asyncio.Event()              # a shared stop flag
        self.running = False

    async def prompt(self, text):
        if self.running:                           # one run at a time
            raise RuntimeError("Busy: use steer() or follow_up()")
        self.running = True
        self.cancel.clear()
        try:
            self.messages.append({"role": "user", "content": text})
            await run_agent(self)
        finally:
            self.running = False

    def steer(self, text):      # delivered after the current turn's tools
        self.steering.append({"role": "user", "content": text})

    def follow_up(self, text):  # delivered only when the agent would stop
        self.follow_ups.append({"role": "user", "content": text})

    def abort(self):
        self.cancel.set()

Inside the loop, three spots change:

        if agent.cancel.is_set():                    # checked before each model call
            return
        ...
        results = await asyncio.gather(              # all calls at once; results keep
            *(run_tool(c, agent.tools, truncated) for c in calls))   # the input order
        ...
        agent.messages += agent.steering; agent.steering.clear()     # steer after tools
        if not calls and agent.follow_ups:                           # would stop, but
            agent.messages += agent.follow_ups; agent.follow_ups.clear()  # work is queued
            continue

The cancel flag is like a "stop training" flag that a training loop checks every step. pi uses an AbortController, the browser's standard version of the same idea (packages/agent/src/agent.ts:512), and passes its signal down to the provider and to each tool.

§9Step 7 · A coding agent

Problem. Steps 0–6 give a general agent with one toy tool. To do "what pi does today", it needs real hands, instructions, memory that survives a restart, and a plan for when the transcript outgrows the context window.

Idea. None of this changes the loop. The coding agent is the Agent class plus tools, a system prompt, subscribers and hooks (Fig 4).

PieceWhat it doesWhere
Toolsread, bash, edit, write are on by default; grep, find, ls also existcoding-agent/src/core/settings-manager.ts:215, core/tools/
System promptopens with "You are an expert coding assistant operating inside pi", then lists tools, guidelines, project files and the working directorycore/system-prompt.ts:147, :9-32
Project instructionsloads AGENTS.md or CLAUDE.md into the promptcore/resource-loader.ts:185
Session fileone JSON line per entry, appended to <timestamp>_<id>.jsonl; resuming replays itcore/session-manager.ts:1080, :1187
Compactionwhen context tokens exceed the window minus a 16,384-token reserve, older history is summarizedcore/compaction/compaction.ts:128, :267-269
Extensionsuser plug-ins reach the loop through the hooks from Step 5core/agent-session.ts:625-654

Two of these match patterns you know from data systems. The session file is an append-only event log, so a crash loses at most the last line, and resuming is a replay, like restoring from a checkpoint. Compaction is lossy summarization of old history, the agent's version of a bounded buffer. Why the agent needs it: the transcript only ever grows (§4), but the context window is fixed.

So where does quality come from?

My summary of the code: the loop is roughly the same in every agent. The differences are in tool design (clear descriptions, readable errors, truncated output), in what the prompt and context contain, and in safety hooks. That is where most of pi's tool code goes: bash.ts alone is 442 lines.
